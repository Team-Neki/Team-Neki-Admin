## 수집 범위와 데이터 계약

- 한 레코드는 `공식 출처의 게시물/프레임 항목 1건`이다. 브랜드 간 같은 콜라보라도 원문 게시물은 별도 레코드로 둔다.
- 필수: `id`, `externalId`, `brandId`, `brand`, `sourceKey`, `sourceUrl`, `title`, `kind`, `observedAt`, `fingerprint`.
- 선택: `publishedOn`, `startsOn`, `endsOn`, `rawDateText`, `imageUrl`. `sourceStatus`는 원문 제목에 종료가 명시됐을 때만 `ended`, 그 밖에는 `unknown`이다.
- `availability=unverified`가 기본이다. 날짜가 있더라도 지점별 적용·조기 종료·공지 변경을 확인하기 전에는 촬영 가능 여부를 확정하지 않는다.
- 원문 URL과 출처별 외부 ID를 합쳐 중복 제거한다. 제목만으로 합치지 않는다. 원문 내용의 해시가 바뀌면 재검토 상태로 되돌린다.
- 종료일 공란, 연도 불명, 이미지 안 날짜, 지점 한정, 행사 렌탈은 자동 게시 금지 항목이다. OCR을 붙이더라도 추출 근거와 사람이 확인한 값을 구분해야 한다.
- 이미지 URL은 원문 참조용이다. 프레임 이미지를 저장·재배포하려면 권리 확인이 선행되어야 한다.

서버 저장 모델은 `source`(공식 채널과 수집 상태), `candidate`(브랜드·원문 ID·정규화 값), `candidate_revision`(원문 변경 이력), `review_decision`(승인·반려·수정과 담당자)로 나누는 것이 적절하다. `candidate`의 유일 키는 `(source_key, external_id)`다. 게시물이 첫 페이지에서 사라져도 자동 삭제하거나 종료 처리하지 않는다. 승인된 항목만 별도 조회 API로 내보내고, 수집 실패와 0건을 구별해 마지막 성공 시각을 유지한다.

이전 `scripts/frame-collector/`는 포토시그니처, 하루필름 3개 포트폴리오 게시판, 포토매틱을 대상으로 공개 HTML을 읽었다. 현재 실행 코드는 위 독립 모듈로 옮겼으므로 당시 루트 실행 명령은 더 이상 사용하지 않는다.

1. 출처별 파서가 게시물 후보를 추출한다.
2. 공통 필드와 날짜를 정규화한다. 증거가 없는 날짜는 `null`이다.
3. 외부 ID로 upsert하고 `fingerprint` 변경을 감지한다.
4. 결과는 JSON 상태 파일에 원자적으로 저장한다. 한 출처라도 실패하면 상태 파일을 갱신하지 않는다.

## 운영 연결 전 필수 작업

1. 서버의 공유 영속 저장소 또는 별도 데이터 API를 정한다. 현재 `.data/`는 로컬·단일 인스턴스용이며 배포 간 공유를 보장하지 않는다. 기존 Amplitude 캐시도 기본값이 컨테이너 로컬 파일 경로이고 공유 볼륨 설정은 이 저장소에 없다. 관리자 화면은 검토 승인된 레코드만 읽도록 한다.
2. 승인·반려·수정 이력을 저장할 API와 권한을 마련한다. 수집기가 검토 상태를 무시하고 공개 화면에 직접 쓰지 않게 한다.
3. 수집 실행은 서버 스케줄러 또는 GitHub Actions `schedule`로 하루 1회부터 시작한다. 재시도, 마지막 성공 시각, 출처별 0건/오류 경보를 둔다. GitHub 예약 실행은 [지연·누락될 수 있다](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).
4. 현재 비활성 출처는 공식 웹 피드 또는 실제 브라우저에서 읽을 수 있는 공개 게시물의 추출 가능성을 검증한 뒤 어댑터를 추가한다. API는 필수 조건이 아니다. 로그인·접근 제한·인증서 검증을 우회하지 않으며, 원문 수집과 이미지 재배포 권리를 구분한다.

Codex 자동화는 정형 수집의 실행기가 아니라, 새 출처 탐색·이미지 날짜 판독·출처 변경 검토에 적합하다. 핵심 수집과 저장은 재현 가능한 코드와 서버 스케줄러로 운영한다.
